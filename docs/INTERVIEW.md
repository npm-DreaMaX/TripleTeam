# 项目定位与面试材料

## 一句话

**TripleTeam：面向长程软件工程任务的自适应执行与可信交付系统。**

服务的任务类型是：目标与验收边界相对稳定，实施路径要逐步发现，多个阶段/模块存在依赖，失败后需要保留有效进展。跨模块功能、复杂缺陷、重构和升级都属于候选场景；SDK 迁移只是其中一个例子。

交付形态是独立 CLI + 本地 daemon。Pi 提供执行内核；TripleTeam 维护跨多次执行的工程事实、资源决策、合同证据与交付状态。内置 Pi extension 是 worker 的控制工具适配器，产品本身不依赖插件宿主。

## 我的贡献是什么

可以明确署名的贡献是**预算与验证约束下的工程执行决策闭环**：

```text
观察任务依赖、接口证据、失败、预算
→ 选择单执行 / 并行 / 串行 / 调查
→ 执行并保存 Candidate
→ 检查具体代码树
→ 判断重试、改计划、复验或停止
→ 只有证据允许时才集成与交付
```

Pi 的 provider、agent loop、tools、session 和 compaction 是复用的。原创实现包括有效 profile/上下文绑定、逐事件计费与共享预算、控制工具的权限边界、执行策略、artifact-backed contract、失败后的 Candidate 复用及验证收敛。这些能力与现有 Pi 公共 API 组合，形成项目针对长程任务的 harness 改进。

新增的独立验证把计算分配进一步延伸到**先明确行为、再实现、再证伪**：公开规格引用形成可检查义务，共用断言的可执行错误对照检验检查能否拦截所指缺陷，通过后才购买独立上下文批判，冻结定义在候选和最终树上复用。先执行低成本、确定性的校验，可以避免为格式或运行错误继续支付模型审查费用。验证计算与 writer 计算分账，成功/失败按实际 writer Attempt 计数。这些是具体的策略和反馈设计；模型生成检查仍可能误解要求，因此保持补充证据等级。

**面试不要用“全部自主、不需要人”定义价值。**开发者仍决定无法从规格与仓库唯一推出的产品语义和权限；系统应承担普通搜索、调试、测试、失败恢复与进度维护。自主评测关闭人工入口，BLOCKED 仍计未完成。

## Multi-Agent 在哪里可能值得

| 任务状态 | 合适行动 | 收益来源 | 应付出的代价 |
| --- | --- | --- | --- |
| 已有稳定、可检查的共享接口，多个消费模块独立 | 并行实现 | 减少等待，缩短完成时间 | 多上下文、检查和集成 |
| 一个未知会影响多个下游实现 | 有区分度的调查 | 避免多份错误实现 | 调查调用及读取成本 |
| writer 与自测可能共享一个错误理解 | 独立规格与反例设计 | 提前暴露输出格式、边界和兼容要求的偏差 | 设计、批判和重复执行费用 |
| 高度共享可变状态或核心设计未稳定 | 单 writer / 串行 | 避免假并行返工 | 放弃部分并发 |
| 已有大量正确代码，少量验证失败 | 保留 Candidate 后定向修复 | 累积有效进展 | 再次验证 |
| 已发布接口实现需要修改 | 计算影响闭包并复验 | 允许兼容演进且保留可追溯性 | 生产者和消费者的复验费用 |

额外 Agent 的自然收益常常先体现在时间上，未必省 token。若主张同时更准、更省，就需要固定模型/工具/预算的消融，以及原生产品配置的端到端对照。

## 用户为什么采用

有明确交付目标、可配置验收、有跨执行管理负担的仓库任务，是合理的试用对象。开发者得到统一目标状态、持久候选、失败证据、预算账本和可核对的最终 Git 产物。

是否值得替代已有 Codex/Claude Code 工作流，最终看同条件完成率、总成本、交付时间和人工投入。当前项目已经有可演示机制；竞争优势仍是待测假设。不能把竞争产品描述成不支持非交互执行、恢复或子 Agent，也不能用未运行的对照声称更强。

## 简历示例：无需虚构结果

**TripleTeam｜长程软件工程 Agent 执行与可信交付系统｜个人项目**

- 针对跨模块任务中重复探索、接口失配与复验开销，实现预算约束的自适应执行策略；结合 DAG 关键路径、任务耦合、运行失败和成本历史选择单 writer、并行实现与有界调查，持久化每次决策依据。
- 设计 artifact-backed coordination：将接口声明绑定到 Git tree、文件内容/权限及指定检查，记录消费者使用的版本与证据；接口实现变化时复验生产者及传递依赖闭包，阻止未经证明的修改进入集成。
- 基于 Pi 公共 API 实现执行与交付闭环，复用模型与会话运行时；通过 Candidate 保留、差异化失败处置、epoch fencing、串行 CAS 和最终树验收支持受控重试与恢复。
- 建立无人工评测协议、共享用量账本、FeatureBench 与 SWE-Milestone 适配及可复现基线；实现故障/权限/证据绑定回归测试。性能数字待冻结对照实验后填入。

可以将第三条展开为独立验证贡献：在实现前形成 source-cited behavior obligations 与 executable probes，共享断言的错误对照和独立批判均通过后冻结；通过完整评价批次和最终 Git tree 门禁阻止旧证据或中断结果被复用。两次真实 Pi + DeepSeek 受控运行已经完成交付，见[运行记录](validation/2026-09-23-controlled-runtime.md)；另一次[双模块运行](validation/2026-09-23-two-module-runtime.md)记录了独立检查发现错误、writer 自动修复和最终交付。该证据说明系统链路可运行，不代表相对 Codex/Claude Code 的提升。

正式测完后，第四条可替换为：在**明确数据版本、实例数与预算**下，相比**明确产品/模型配置**，完成率 `[结果]`，全部试验费用/成功数 `[结果]`，限时完成率 `[结果]`；注明消融与置信范围。未完成的单题盲测不能用作这条提升数据。

## 十分钟讲解顺序

1. **问题与失败案例，1 分钟。**两个 worker 分别正确，但使用了不同接口假设；或者各自候选通过而最终组合失败。
2. **决策模型，3 分钟。**说清状态、可选动作、收益/成本代理、共享预算和无进展止损；承认当前估计器是启发式。
3. **合同落地，2 分钟。**演示“聊天承诺→未满足”“准确产物+检查→可消费”“变更已发布产物→闭包复验”。
4. **收敛与恢复，2 分钟。**展示失败保留 Candidate、生成定向修复、拒绝 stale execution、最终检查失败不会 Done。
5. **实验与反例，2 分钟。**两个对照层次：相同 Pi/模型研究策略贡献；原生 Codex/Claude Code 研究用户价值。报告一个不值得并行的例子和本次盲题未通过的事实。

## 哪些内容弱化

- SQLite 表数、daemon endpoint、worktree 数量只用于解释决策为何可靠。
- 不把角色数量、消息路由、状态机长度当算法贡献。
- 不宣称训练、强化学习、最优性或 SOTA；实现中不存在的能力不能照搬参考简历。

最值得深入的追问是：**哪一次追加计算因新证据而改变方向；它避免了什么无效工作；省下的代价是否足以覆盖新增协调与验证。**用真实轨迹和预先冻结的消融回答，才会把系统实现转化为有说服力的 Agent 项目。
