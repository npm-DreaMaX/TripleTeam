## 1. 总判断

**问题选得有价值，工程基础已经形成，算法贡献和收益证据尚未成立。当前最值得投资的是让完整任务的执行与交付闭环成立，并用受控实验验证核心协调决策。**

你已经实现了以 Pi 为执行基础、以 SQLite 为权威状态、以 Git artifact 和外部检查驱动交付的本地运行系统。Attempt/Execution 分离、epoch fencing、候选快照、串行 CAS 集成、恢复和验收这些设计能支撑严肃实验。单项机制属于成熟工程方法；把它们贯通是实现贡献，不能直接等价为 Agent 算法创新。

1. 同样模型和预算，何时比一个强单 Agent 交付得更多、更快？

3. 系统宣称通过验收时，实际交付是否满足独立验收标准？

第 3 项还存在确定缺陷，应先修；第 1、2 项需要机制改进和受控实验。现阶段是**已有运行基础的开发者工具原型**，核心方法和产品优势需要通过真实任务继续验证，尚无足够证据证明用户应该迁移工作流。

## 2. 问题够不够前沿，以及已有研究意味着什么

这个方向处在 Agent test-time compute、协作可靠性和软件工程验证的交叉点，但“多 Agent 不一定更好”已经是公开研究结论，不能单独作为新贡献。

- **Towards a Science of Scaling Agent Systems** 研究任务结构与协调方式的匹配，并发现工具开销、顺序依赖等因素会影响扩展收益。它覆盖的任务领域不等同于本项目的软件工程任务，其数值不能直接当作这里的性能依据。[论文](https://arxiv.org/abs/2512.08296)
- **CATS** 已研究预算下串行与并行探索的计算分配，主要对象是搜索型工具 Agent。因此，“自适应选择串行/并行”这一宽泛表述已有明确相关工作。[作者机构页面](https://research.google/pubs/cost-effective-agent-test-time-scaling/)
- **CooperBench** 把协作编码的承诺偏离、错误预期和沟通失败变成可测问题，直接支持你研究接口兑现和协作损耗的动机。[论文](https://arxiv.org/abs/2601.13295)

建议把研究问题收窄为：

> 在软件状态持续变化、验证成本较高、Agent 结果不可靠的条件下，如何依据可验证接口和运行证据分配下一份计算，提高固定预算内最终工程目标的完成率？

这里有一个值得研究的区别：软件任务的收益取决于**最终可集成、可验收的代码状态**。多个局部正确答案不能直接相加。契约、集成和复验既消耗预算，也改变下一次行动成功的概率。

这是适合面试讲述的研究方向；是否形成新方法、是否优于已有方法，仍需实验和进一步文献对照，不能预先写成已证明结论。

### 3.1 Adaptive Coordination 目前回答了什么

`src/control/coordination-policy.ts:25` 和 `:56` 主要依据 HIGH/LOW 标签、字符串交集、scope 和 coding lane 上限贪心选任务。

它能判断某些显式条件下应保守串行，也能记录决策依据。当前没有估计增加一个 Agent 的成功率增益、耗时缩短、探索重复、集成拥塞和验证增量；资源快照写入决策记录不等于这些信息已经参与收益计算。

其他具体限制：

- DAG 用于判断就绪，未估计持续时间或关键路径。
- 高不确定任务的探索优先于本轮所有 writer，包括其他无关的就绪任务。
- `scheduler.ts:100` 等待整个 `Promise.all` 批次结束才重新调度。若 A 需 10 分钟、B 需 1 分钟、C 依赖 B，则 C 可能等到 A 结束；这会吞掉已有并行收益。
- 初始 assessment 没有形成探索后重新估计的闭环；追加任务的协调信息也未完整贯通。
- `DIVERSE_EXPLORATION` 实际执行多个只读问题。`hypothesis` 被记录，但没有传入 explorer prompt；缺乏对竞争假设的证伪、选择和综合机制。

这些是有用的 baseline，但尚不足以支撑“知道下一份 compute 是否值得”的强表述。

### 3.2 CoordinationContract 的关键缺口

`kernel.ts:440` 附近持久化的 provides/requires/interfaces 是字符串数组；缺少逐项 artifact 兑现关系、schema hash、消费版本和对应的证明检查。

更直接的问题是 `kernel.ts:2562`：Task 被接受时，关联契约直接更新为 `SATISFIED`。这里没有逐条证明 provides 已实现、requires 所绑定版本可用或 assumptions 仍成立。

此外，requires/provides 的字符串匹配用于禁止并行，却不会自动建立生产者先于消费者的依赖。Planner 一旦漏写 DAG 边，消费者可能先执行。

因此，**Candidate 绑定 exact tree 已有代码，语义承诺绑定可执行证据仍需实现**。两者必须分别证明。

### 3.3 Failure Policy 的标签与动作之间还有距离

`failure-policy.ts:126` 将多个 disposition 归为 `retryTask=true`；之后常见执行路径仍是启动同一 implementer profile 的新 Attempt，把上次结果放进反馈。

- 普通 RETRY 有反馈，值得保留。
- 部分基础设施检查有同树重试，属于真实动作。
- DELEGATE 主要承接已经存在的任务图提案。
- REPLAN 没有保证调用规划器或实际修改计划；标签只能影响提示。
- 集成冲突后的 REBASE_REVERIFY 可能变成重新启动 writer，没有稳定复用原候选修复的专门路径。
- `scheduler.ts:65` 附近最终验收失败直接 blockRun，绕过 Failure Policy。普通工程回归因此可能需要人工接手。

需要将动作定义为可审计的状态转移和产物，而不仅是下一轮 prompt 中的文字。

### 修复 R2 时需要避免的遗漏

检查前后 Git diff 相同仍不能排除“临时修改、测试、再恢复”。根据要保证的强度，使用可信检查器与受约束的源码视图。允许编译产物写入专用目录，无须要求所有文件系统写操作为零。

此外，冻结 `npm test` 的 argv 没有冻结它引用的 package.json、测试文件和配置。Agent 可以无意削弱测试、更新快照或改脚本。至少区分：基线回归检查、可信验收检查、Agent 新增自测、外部 evaluator。每条 evidence 记录验证了哪个 obligation、oracle 来源与版本。测试通过的保证范围应明确限定为这些检查覆盖的行为。

## 5. 代码审查发现、但本次未做完整动态复现的风险

这些结论的证据级别与上面的 R1–R7 不同，不应描述为真实模型运行已触发。

1. **恢复上下文身份混入动态反馈。** `task-executor.ts:319` 重新生成 feedback，`:505` 将完整 prompt hash 作为 contextManifestHash；kernel 又要求同一绑定 hash 不变。消息 readAt、探索记录或其他动态反馈变化可能使合法恢复失败。应持久化初始 manifest，用独立 delta 注入新证据。
2. **resume 与 execute 的控制逻辑分叉。** resume 没有复用 execute 的人工请求/任务提案处理链。应共享“worker 结束后的判定”步骤，覆盖恢复期间提出产品问题的场景。
3. **失败执行成本漏记。** Pi usage 在 worker.run 正常返回后才写入 usage_records；超时或崩溃已经消耗的 token 可能未落库。Pi 事件应经现有适配器增量持久化，不重写 Pi 的计费或事件循环。
4. **完成与验收边界有待收紧。** 内核部分门禁依赖上层调用顺序；例如 completeRun 接收调用者传入的 treeHash。建议以权威 head 派生、校验上下文，并补跨模块不变量测试，避免只测各函数 happy path。
5. **探索状态与版本匹配不完整。** 已完成探索的读取以 key/baseline 去重，未严格匹配当前 task revision/hypothesis；反馈还包含旧 baseline 的探索。应标注适用版本与失效原因。
6. **恢复验证仍有限。** 历史真实 E2E 证明过一些恢复路径；当前策略、反馈和 DecisionRequest 是后续加入。需要当前版本的定点故障注入。Pi RPC 在 stdin 结束时执行 shutdown，不能仅凭控制进程退出便断言一定遗留可写 worker。

`REAL_E2E_VALIDATION.md:5` 已明确声明上层策略在五个真实场景后新增，这一点记录得诚实。该材料证明底层流程可运行，尚未证明当前策略收益、复杂项目长程稳定性或 benchmark 性能。

## 6. 推荐的新主线：以验收结果驱动计算分配

建议使用一个明确主问题统领现有模块：

> 在给定计算预算、时间约束和授权边界内，最大化软件工程目标通过外部验收的概率。

对任务集合，Verified Engineering Throughput 可以定义为固定时间/资源配置下完成的**外部给定目标**数。不要统计 Planner 自己拆出的 child Task 数，否则拆得越碎指标越高。任务难度与价值权重必须事先确定。

至少并列报告：

- 固定总预算下的独立验收成功率；
- 固定截止时间下的完成率及成功交付时延分布；
- 总费用除以成功交付数，失败运行的成本也计入；
- 错误验收率、阻塞率、人工实际操作时间。

不宜一开始把它们压成一个任意加权分数。先展示成本、延迟、质量的 Pareto 关系，并明确部署场景偏好。

### 6.1 把每次决策定义为有结果的行动

决策单位应是一次有预算上限、可以观测结果的计算行动：继续实现、执行诊断测试、调查一个未知点、冻结一个接口、并行实现两个子任务、修复已有候选、停止或请求必要授权。

把 `SINGLE/PARALLEL_TASKS/SERIALIZE/DIVERSE_EXPLORATION` 保留为执行模式，另记录：

```text
当前状态与证据版本
可选行动及预计成本
选择理由和预测结果
预留预算 / 停止条件
实际 token、工具、检查、集成和等待成本
产生的新证据
最终目标是否通过独立验收
```

对额外行动 a，比较它与“继续当前强单 Agent”的增量效用，例如：

```text
ΔU(a | s) = E[最终验收收益 − 费用惩罚 − 截止时间损失 | s, a]
            − E[同一效用 | s, 继续当前执行]
```

这是待估计的决策定义，不是当前已实现公式。预测应包含额外实现、重复探索、候选选择、集成、复验及失败恢复成本；集成和检查队列同样消耗关键路径时间。

高不确定性本身不能推出“应该多开探索”。需要考虑：这次探索能否改变下一步选择，改变选择预计能避免多少浪费。低价值未知点可以保持未知。

### 6.2 先做可测、可解释的估计

首版增强可使用简单模型和明确规则：

| 信号 | 可观测来源 | 用途 |
| --- | --- | --- |
| 依赖与剩余关键路径 | DAG + 各类任务历史耗时分布 | 判断并行是否缩短完工时间 |
| 接口/测试影响交集 | import、类型/schema 引用、测试映射、变更历史 | 估计兼容性风险；这些仍是代理信号 |
| 集成与复验负担 | 最近检查时间、集成队列、候选过期频率 | 避免制造超过消费能力的候选 |
| 新信息与重复失败 | 失败 test identity、诊断变化、已验证假设 | 选择继续调试还是切换方法 |
| 剩余预算 | 各执行增量费用 + 已预留额度 | 在启动前约束，而非结束后才记账 |

Planner 的等级判断作为一项特征，不能直接视为真值。采集数据后，先做耗时/失败概率回归和校准，验证比现有启发式更好再增加模型复杂度。

**不建议为增加“算法味”直接上强化学习。** 先定义状态、动作、奖励、可比较 baseline 和观察窗口。历史确定性策略只记录被选择动作，不能据此知道未选动作会怎样；要用配对快照、受控随机分配、重复运行获取比较依据。任务之间有干扰、最终奖励延迟，也不能未经论证套用独立 bandit 假设。

### 6.3 让契约创造并行机会

当前语义耦合通常导致串行。更值得研究的是：**花一小份计算先产出可检验接口，能否降低后续协作成本，使原本耦合的任务可以并行？**

例：后端需要提供 UserProfile，前端需要消费它。

1. 先产出一个小的接口 Candidate：类型/schema、错误语义、必要例子和契约检查。
2. 对该 Candidate 验证，获得版本化接口事实。
3. 后端和前端明确绑定同一接口版本；在允许的情况下从共同已验证 checkpoint 开始并行。
4. 消费方使用与 schema 一致的 mock；mock 必须再与真实 provider 做兼容性检查，防止自洽但错误。
5. 接口变化生成新版本，识别受影响的消费义务；旧 acceptance 保留为旧树历史事实，当前最终目标重新验证。

最小契约可以限定为一种语言/接口，不需要通用 DSL：

```text
contractId / version / producerTaskRevision
interfaceBlobHash 或 schemaHash
producerCandidateTree / verifiedCheckpoint
obligation -> checkDefinitionVersion -> checkRunId
consumerTaskRevision -> consumedContractVersion
invalidationReason / replacementVersion
```

其中 obligation 需要显式语义与检查，不是凭 hash 自动理解代码。运行开始时声明哪些内部接口可由系统自行决定，避免把每个技术选择都变成人工请求。

这是三个卖点可以连成因果链的地方：先花计算降低耦合 → 选择可获益的并行 → 以接口和最终检查约束结果 → 测量返工与交付变化。没有实验前应将它称为本项目拟验证的假设。

### 6.4 任务拆分必须考虑“能否独立通过验证”

按目录拆成两个 writer 不意味着可以依次独立验收。A、B 可能只有共同变更才通过最终行为检查：例如旧接口删除和所有调用方迁移。

此时有三种可选择策略：

- 加兼容层，让每个中间状态可验证；
- 保持一个实现任务，由多个只读调查者提供证据；
- 形成明确的候选集成组，在临时树联合验证后，串行 CAS 发布整个组。

集成组不能绕过最终冻结验收，也不能把未兑现的子任务先标 ACCEPTED。要评估组失败后的返工和定位成本。这个问题比“用几个 Agent”更接近软件工程的实质难点。

### 6.5 失败必须触发不同的实际工作

| 证据 | 下一步动作 | 必须产生的结果 |
| --- | --- | --- |
| 同一候选的环境错误 | 有界 INFRA_RETRY | 保持源码树不变，新的检查证据 |
| 新的确定性 assertion failure | 聚焦修复或诊断 | 可定位失败原因和新候选 |
| 相同失败、无新信息 | 改假设/改计划 | 不同诊断或任务图变化记录 |
| 接口不一致 | 更新/修复契约及受影响任务 | 新接口版本与兼容性证据 |
| baseline 变化 | 复用候选尝试重放、冲突修复、复验 | 明确派生关系的新 Candidate |
| 最终目标回归 | 创建 run 级 repair Task | 在原冻结目标下的新最终树和验收 |
| 预算耗尽或缺少授权 | 停止或 DecisionRequest | 可解释的阻塞原因与已有交付材料 |

旧候选和失败日志应成为下次行动的可复用输入。每次失败重开一个 writer、重新探索整个仓库，会使“失败自适应”反而成为 token 放大器。

## 7. 人类介入、产品价值与 Codex / Claude Code

### 7.1 有人参与，并不使自动化失去价值

可操作的目标是：**在用户事先给定的语义、权限和验收范围内，系统自行处理技术执行和修复，把必须由用户决定的事项明确提交。**

应区分三类中断：

1. 真正的产品或权限选择，例如已有 spec 无法确定兼容性承诺。这属于必要决策。
2. 工程上的困难，例如测试失败、依赖未发现、计划不合理。应先使用已授权预算自主处理。
3. 系统实现缺陷，例如本次 R5/R6 导致有效批准无法恢复。这必须修复，不能解释为 Human-on-Exception。

当前 proposal policy 将所有 revision/cancellation 一概归为用户可见意图变化，会把部分技术重规划也推给用户；同时 R4 又允许子任务扩大 scope。根源是缺少清晰的 **run 授权边界与 task 内部分工边界**。二者应分别建模：技术路径可以变，用户语义和权限不能被悄悄变更。

产品指标应包含必要/不必要的人工请求、用户实际操作分钟、阻塞等待、无人干预成功率。当前 HUMAN_WAIT 记录的是等待时长，不能当作人类劳动时间。

### 7.2 用户为何使用这个系统

Codex 官方已经提供并行 subagent 工作流和 worktree；文档明确提示子 Agent 会增加 token 消耗。[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)

Claude Code 的公开 agent teams 文档同样讨论共享任务、独立上下文、相互沟通，并明确指出顺序依赖强或编辑冲突高时收益会下降。这只能作为公开产品行为依据，不能据此声称掌握其内部算法或事务控制实现。[Agent teams](https://code.claude.com/docs/en/agent-teams)

因此，并行、角色、worktree、自动调用工具本身很难形成足够迁移动机。建议围绕**目标可验收、实施路径需要动态发现、多阶段工作相互影响的复杂工程任务**建立产品闭环，并用跨模块功能开发、重构、缺陷修复和迁移等不同案例验证收益。具体案例应体现运行时间、返工和复验等真实成本。

潜在承诺可以是：

- 用户事先设定预算、授权范围和验收要求。
- 系统选择继续单执行、提前确认接口、并行实现或定向诊断。
- 用户获得确定版本的交付、完整证据与费用说明。
- 发生故障后，系统保留已完成工作和权威边界，继续收敛。

这些承诺仍需试用与测量。若在目标场景中强单 Agent 成本更低、完成率相当，就应选择单 Agent；如果所有目标场景都如此，说明研究假设需调整。项目允许得到“有些任务额外 Agent 没价值”的负结果。

现阶段不建议同时建设通用 SaaS、IDE、角色市场和多 runtime 抽象。保留 Pi 执行边界，把 Codex/Claude Code 作为参考和外部对照对象。开发者工具原型与成熟产品的成功标准不同，面试项目可以围绕实际工程任务和可验证的方法贡献展开，商业采用理由继续通过试用验证。

## 8. Benchmark：需要关闭人类回答，并冻结协议

公开 benchmark 的选择、与 Codex/Claude Code 的比较口径及接入验收见 [BENCHMARK_PLAN.md](BENCHMARK_PLAN.md)。该方案已核对公开资料和部分评测源码，尚未实现 adapter 或运行正式评测。

**要。自主能力评测必须有 noninteractive 模式；仅隐藏提问按钮不够。**

建议在 run 初始化时冻结以下字段：

```text
decisionMode: interactive | noninteractive | scripted_oracle
goalContractVersion / authorizedScope / oracleVersion
model / provider / toolProfile / environmentVersion
tokenOrCostBudget / deadline / maxExecutions
policyVersion / seed / datasetInstance
```

这些是建议新增项，并非当前配置已支持。

- **noninteractive**：运行途中没有人类答复或 steer；运行仍可记录 DecisionRequest，遇到无法授权的问题应及时返回 BLOCKED。预算内可解决的技术困难应自主处理。
- **interactive**：用于实际产品，记录人工介入和实际耗时；结果单列。
- **scripted_oracle**：只有评测前预先固定的答复；不能由人临场帮解题，也不能访问隐藏测试给答案；属于辅助条件，不能混入完全自主成绩。

模式须约束所有入口：CLI/daemon 的决策、人工消息、恢复时的新输入，以及其他能影响运行的渠道。不能在控制面写着无人工、实际由操作者改仓库或重跑命令。取消和基础设施运维也应记录，保持可审计。

### 8.1 防止把自身判断当作评测标签

benchmark 成功必须由独立 evaluator 在最终交付 commit 上判定。`VERIFIED_DELIVERY` 是系统输出，应同时检查它和外部结果是否一致，单列 false acceptance。

完整统计超时、BLOCKED、取消、崩溃及失败成本，不能只比较成功的运行。对常规自主完成任务，BLOCKED 留在成功率分母内；另外设计“必须请求产品/权限决策”的例外集合，评估正确暂缓，避免把擅自猜测奖励为自主性。

隐藏验收测试不放进 writer 可读 workspace。可见检查用于开发反馈，隐藏检查用于独立评分。记录检查器版本、环境、最终 tree，避免将检查名或退出码当作覆盖证明。

### 8.2 至少包含这些对照

| 对照 | 目的 |
| --- | --- |
| 强单 Agent + 同一 runtime/检查/恢复基础 | 隔离协调策略的增益；允许充分 debug/retry，使用相同总预算 |
| 固定并行数 + 同一模型和基础设施 | 判断动态分配是否确实改善固定策略 |
| 当前 HIGH/LOW 启发式 | 作为现有实现基线，验证增强策略值得增加复杂度 |
| 增强计算策略 + 可执行契约 | 候选方法 |
| 原始 Pi 单执行，可选 | 单独测运行系统本身的工程增益，不能代替公平的策略对照 |

基座模型、版本、工具、环境、可见信息和总计算口径保持一致。计算包含 planner、explorer、writer、reviewer、候选选择、失败执行及恢复。token 与 dollar 都记录，工具/测试机器时间也单列；缓存计费差异不能忽略。

分别绘制“固定预算的完成率”与“固定 deadline 的完成率”曲线。不要要求既完全相同实际 token 又完全相同实际运行时间，再把不可比的运行筛掉。

与 Codex/Claude Code 的端到端产品对照另列：若模型、工具或权限无法对齐，应公开这些差异，不能把差异归因给单一算法。

### 8.3 数据与实验设计

先用小规模开发集检查流程、成本和失败类别，再在未参与调参的仓库/任务集合测收益。可以从 20–30 个实例的 pilot 开始估计方差和费用，之后依据观察结果与预算确定正式样本量；小 pilot 不能支撑普遍优越性。随机性较大时做多次重复，报告配对差异和置信区间，明确任务与仓库聚类。

覆盖至少四种结构：

1. 清晰独立的多模块任务：应能观察并行收益。
2. 强依赖链：应选择少量 writer，避免无效扩张。
3. 文件不相交但接口耦合：验证契约能否改善兼容性。
4. 高不确定或易失败任务：验证诊断/探索行动的预算价值。

另设可重复的故障注入集：进程退出、检查超时、陈旧 head、接口变更、检查器修改源文件。这一集证明系统保证，不能取代真实软件任务的算法收益评测。

关键消融：

- 自适应策略开/关；
- 可执行契约替换成聊天/字符串声明；
- 保留相同预算、将失败处理改为普通重试；
- 接口先行与直接实现；
- 有/无增量证据复用（最后仍执行完整验收）。

不仅报告最终分数，还报告重复探索开销、失败后返工、接口不兼容次数、过期候选比例、验证与集成耗时、空闲 worker 时间。只有中间机制指标和最终收益同向变化，因果解释才更可信。

### 8.4 CooperBench 的适用边界

CooperBench 适合测双任务兼容性和承诺兑现；其协议包含各 Agent 初始可见需求的边界，隐藏测试与参考解不提供给 Agent。论文允许 Agent 通过协调重新分工。[协议 §2.1](https://arxiv.org/html/2601.13295v2)

若把两份需求一开始同时给中心 Planner，并允许任意选择一个 Agent 完成全部工作，应明确这是基于 CooperBench 任务的自适应执行评估，与原始双 Agent 合作条件不同。可以保留官方条件作一条实验轨道，再另列项目自己的条件；不能改了信息结构后直接声称打败官方合作成绩。

CooperBench 仍然只应作为 evaluator adapter。它不充分覆盖长程恢复和多阶段 DAG，后者需要独立评测。

## 9. 值得保留、弱化和暂停的工作

| 模块 | 建议 |
| --- | --- |
| Pi 适配、固定依赖、公开 API | 保留；它让研究变量集中在协调策略，面试时简短说明边界 |
| Task/Attempt/Execution、epoch、Candidate、CAS | 保留为系统保证；用一个故障场景讲清价值 |
| 验收、artifact/evidence、最终交付 | 优先修正；这是所有收益指标的可信基础 |
| CoordinationContract | 聚焦一种接口，补真正可执行的兑现和版本消费机制 |
| Adaptive Policy | 聚焦边际收益、关键路径与验证成本；先做强 baseline 和数据 |
| Failure Policy | 缩短到真正实现的几种动作，再逐步增加 |
| Planner | 增加可验证性、接口边界和任务粒度意识，少增加角色 |
| Human-on-Exception | 做成权限和语义边界，修正确认后的恢复；不单独包装为算法创新 |
| SQLite/daemon/journal/恢复 | 保留必要功能，面试叙述弱化表数量和枚举数量 |
| GUI、远程集群、泛化多 harness、角色生态 | 暂缓，与当前关键实验无直接关系 |

同样的筛选标准适用于后续功能：它改变了什么可观测决策、避免了哪类浪费、怎样测量？答不上来时先暂停扩展。

## 10. 建议的实施顺序与验收点

### 阶段 A：让现有结论可信

- 修复 R1/R2；将证据类型和检查来源纳入冻结契约。
- 修复 R3–R7，统一 execute/resume 的退出判定。
- 当前版本增加有消息变化、人工决策和探索失败的恢复测试。
- 补失败/中断执行的增量 usage；初始化时冻结真实预算和非交互模式。

**完成标准：7 个探针对应的正确性回归通过；独立 evaluator 与终态一致；崩溃/失败成本不再静默漏记。**

### 阶段 B：建立可解释的基线

- 跑强单 Agent、固定并行、当前启发式。
- 统计总成本、关键路径、重复探索、验证和集成占比。
- 从 pilot 中确定最大的可改善损失项。

**完成标准：能够回答至少两类任务为何加 Agent 获益或受损，并展示完整失败运行。**

### 阶段 C：实现并验证核心决策方法

根据阶段 B 的主要损耗选择方法。以下接口证据与调度改进是一条可执行路线，适用范围需要跨案例验证，并不将产品限制为接口迁移。

- 以一个具体接口类型实现 obligation → artifact → check → consumerVersion。
- 加入“先验证接口，再并行”的行动。
- 使用测得的耗时/返工统计估计收益，保留保守回退。
- 将调度改成任务完成事件后补位，避免整批 barrier。

**完成标准：未见任务上，相比强单 Agent 和当前启发式至少在目标场景改善成本/延迟/成功率之一，清楚报告其他维度的代价；做契约与策略消融。**

### 阶段 D：决定产品承诺

- 找真实用户的同类跨模块任务，记录人工时间和失败处理成本。
- 根据结果决定继续产品化、聚焦研究原型，或收缩到单执行加验证恢复。

这些是带检查点的顺序，不是预设性能提升或开发工期承诺。

## 11. 面试应该怎么讲

### 当前版本可以诚实讲述的贡献

> 我基于固定版本 Pi 构建了一个本地的软件工程运行系统，将长期任务、受控尝试和实际执行分开，用 epoch、不可变 Git 候选、串行 CAS 和冻结验收管理不可靠执行。实现了可解释的协调启发式，并建立了用于研究计算分配和协作失败的实验基础。当前已验证若干系统不变量，算法收益仍在测量。

### 完成阶段 C 后更有说服力的叙事

1. **现象**：增加 Agent 后，省下的实现时间可能被接口返工与复验消耗；展示本项目数据。
2. **假设**：提前验证关键接口能降低耦合，从而改变额外计算的边际收益。
3. **方法**：以契约兑现、失败证据、关键路径和预算为状态，选择下一次计算行动。
4. **机制**：展示同一任务一次“直接并行失败”和一次“接口先行后并行”的完整 trace。
5. **实验**：展示成本—完成率曲线、时延、失败成本及消融；指出在哪些任务上强单 Agent 更好。
6. **可靠性**：演示一个旧 execution 提交被拒绝和一个检查证据失效的案例，说明最终结果的保证范围。

建议叙述时间的大部分用于问题、决策和实验，运行系统只讲支撑这些结论所必需的机制。不要把模块数量、角色数量、状态表数量当作主贡献。

### “我到底做了什么”的直接回答

你当前完成的是**可控执行与证据收敛的工程基础，以及一个初步协调策略**。尚未完成的是**额外计算的可证明收益与具有区分度的决策方法**。

接下来最有价值的成果应是一组能够复现的结论：什么任务应该增加计算、增加哪一种计算、契约如何降低返工、预算耗尽时怎样诚实停下，以及这些选择在独立验收下到底带来多少收益。只要这条链得到实现和实验支撑，就有足够内容深入讨论 Agent 算法；泛化产品的商业成功可以随后验证。
