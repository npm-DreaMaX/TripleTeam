# 面向一类复杂工程任务的系统定位

日期：2026-09-22。本文补充 [代码审查报告](./REVIEW.md)。按用户反馈修订：跨包 API/SDK 升级保留为演示案例，不再作为产品定义或技术栈限制。下文区分目标定位、已有基础和待验证收益。

> 本文保留实施前的定位讨论与设计建议。后续已落实的能力见 [实施结果](../../IMPLEMENTATION_STATUS.md)，当前可直接使用的简历和讲解稿见 [面试材料](../../INTERVIEW.md)。产品边界保持不变，性能收益仍需实测。

## 1. 系统定位

**TripleTeam：面向长程软件工程任务的自适应执行与可信交付系统。**

服务于现有代码库中这样一类任务：**目标有可检验的完成条件，实施路径需要逐步发现，工作涉及多个阶段或模块，并需要多轮验证、修复与集成。**

用户提交工程目标、验收约束和授权范围，系统持续组织执行并保存有效进展，最终交付代码、证据及未解决事项。单个目标可以由一个或多个 Agent 执行；数量与组织方式随任务证据改变。

CLI 是入口，Pi 是执行基础，Task/Attempt/Evidence 是跨执行维护工程事实的模型。项目不按某一种 SDK、语言或迁移操作定义自身。

## 2. 这类问题的边界

“长程”不能只按运行小时数、文件数或 token 数判断。值得重点服务的任务具有以下组合特征：

1. **目标稳定、计划可变。** 需求和验收边界明确，但初始计划会被仓库事实、测试结果和失败推翻。
2. **局部工作相互影响。** 多个模块、接口或实施步骤存在依赖，局部正确不保证最终组合正确。
3. **有效进展需要跨执行保留。** 调查结论、候选代码和验证证据必须带版本，经历重试、切换或恢复后仍能正确使用。
4. **额外计算的收益不确定。** 并行、继续调试、调查未知点和验证候选之间存在取舍。
5. **完成由可检查结果定义。** 系统能依据代码与验收证据推进，而不依赖 Agent 的完成声明。

短小且路径清晰的编辑、纯机械替换可以作为低开销回退测试。缺乏产品目标和验收依据的开放式创意工作，需要先澄清目标。运行边界仍遵守当前本地、单仓库架构，不据此宣称支持跨仓库集群或自动生产部署。

## 3. 多个场景验证同一套系统

| 场景 | 示例任务 | 主要难点 |
| --- | --- | --- |
| 跨模块功能开发 | 为已有应用增加异步报表导出，贯通 API、任务处理、状态查询和前端反馈 | 阶段依赖、接口一致性、端到端验收 |
| 架构调整与重构 | 将同步处理链改为异步执行，并保持约定行为 | 兼容中间状态、实施顺序、回归控制 |
| 跨模块缺陷修复 | 定位并修复重复执行或状态不一致问题 | 假设调查、复现、定位、验证充分性 |
| 系统性升级迁移 | 升级共享 SDK，并适配多个调用模块 | 共享契约、并行机会、语义差异 |

以上是待构建案例，不是当前已经跑通的实绩。它们共同检验任务图、证据、失败与集成机制，无需为每类案例增加一套独立 Agent 系统。

首个 demo 应当足够完整，但不能把首个 demo 当作产品边界。实验应逐步覆盖不同任务结构，检查方法能否跨案例适用。

## 4. 系统级价值主张

**让开发者在给定约束下委托一个完整工程目标，并让多次执行的有效成果持续累积为可验收交付。**

对用户的具体价值包括：

- 持续追踪尚未完成的工程义务、依赖和验收证据，降低任务遗漏。
- 在计划失效、检查失败或执行中断后，保留有效工作并定向处理剩余问题。
- 根据当前证据选择继续单执行、增加调查、并行实现、复验或停止。
- 提供最终代码版本、验证依据、费用记录和需要用户决定的例外。

这些是产品目标。现有代码已有状态、候选、集成、验收和恢复基础；审查发现的缺陷、成本记录缺口和收益证据仍需补齐。

## 5. Multi-Agent 是怎样产生收益的

| 当前任务结构 | 可选行动 | 可能的收益 |
| --- | --- | --- |
| 依赖已满足、接口稳定、有多项独立工作 | 并行实现 | 缩短关键路径外工作时间 |
| 一个未知影响多个后续决策 | 聚焦调查或比较有区分度的假设 | 减少后续错误实现 |
| 不同模块只需要少量共享事实 | 按任务提供相关上下文与版本化证据 | 降低重复探索和假设错配 |
| 高耦合核心尚未稳定 | 单 writer、串行或先处理共同接口 | 限制协调与返工成本 |
| 候选已存在但验证失败 | 定向修复、重放或复验 | 保留已经完成的有效工作 |

收益不自动成立。任务分配、上下文传递、集成和复验都必须计费；额外 Agent 可能让总成本增加。系统的目标是选择值得的行动，并在不值得时保持单执行。

“先验证接口再并行”是一个可验证的策略选项。它不适用于所有任务，也不独占整个系统的算法主线。

## 6. 与 Codex / Claude Code 的竞争关系

对照对象应包括已经配置好项目说明、检查与自动化流程的工具。Codex 支持脚本/CI 中非交互执行和恢复，Claude Code 支持编程调用与继续会话。[Codex 文档](https://learn.chatgpt.com/docs/non-interactive-mode)、[Claude Code 文档](https://code.claude.com/docs/en/headless)

本项目需要证明的采用理由是：在上述复杂任务集合中，明确的工程状态、证据约束和计算策略能降低监督与返工成本，并改善验收成功率、时延或费用。

不能根据公开文档未介绍某个内部机制，就断言其他产品没有该能力。当前也没有数据证明 TripleTeam 已普遍领先。已有用户不需要放弃日常工具，可以按任务选择执行方式。

评价应统计外部工程目标，包含失败和阻塞运行，保持费用和人工操作口径一致。一次更漂亮的 demo 不足以证明竞争力。

## 7. 产品形态与 Harness 边界

| 层次 | 定义 |
| --- | --- |
| 产品 | 长程软件工程任务的自主执行与可信交付系统 |
| 交互入口 | 独立 CLI，可选本地 daemon |
| 自研控制面 | 目标、任务图、尝试、候选、证据、协调策略、集成与交付 |
| 自研执行适配 | 将任务事实转为执行输入、工程工具、失败反馈和恢复条件 |
| Pi 执行内核 | provider、agent loop、通用工具运行、session/history/context、compaction、runtime retry、abort/steer/events |
| 内部 extension | worker 与权威控制面的薄适配器；不改变独立产品形态 |

当前执行基于 Pi，没有把 Codex/Claude Code 接为 worker，也不是它们的插件。Harness 一词范围不统一，简历应明确自己的改动边界。

## 8. 围绕共性难点改进 Harness

### 8.1 任务事实与执行上下文

从同一权威状态投影任务范围、当前契约、已验证成果、未决假设和相关失败，为每次执行提供带版本的证据。动态事实与初始 assignment identity 分开，防止恢复时混淆身份和新反馈。

Pi 继续拥有上下文生命周期、会话历史与压缩。本项目通过公开 API 和工具选择、提交任务相关事实。测量重复探索、过期信息使用、输入费用及遗漏。

### 8.2 可执行的协调和工程工具

在已有协调工具上补充 artifact 兑现、消费版本、检查请求和结构化诊断。Agent 可以提出契约、计划或候选，系统校验并决定何时获得权威效力。

接口验证只是其中一种证据。调查假设、行为约束、回归检查和集成关系也可以进入 Task/Attempt/Evidence，但需要各自明确的验证方式。

### 8.3 面向证据的失败修复

区分实现错误、计划失效、接口不一致、基线变化与环境故障，让不同原因触发不同的实际操作。保留已有候选和有效检查，重新验证受影响部分，最后仍验证最终目标。

沿用 Pi 会话恢复能力；本项目负责判断哪项工作还有 authority、哪些事实仍适用、哪些义务需要补做。测量修复费用、重复失败和进展保留情况。

### 8.4 计算预算与执行策略

通过 Pi 事件增量记录成功、失败和中断执行的成本。结合依赖、关键路径、接口稳定性、检查队列和剩余预算，决定继续、并行、调查、验证或停止。

这四项共同支撑同一类任务，不需要退化为某个迁移工具，也不需要重写 Pi 通用能力。已检查公开 ExtensionAPI 和 RPC 接缝，后续实现继续遵守固定依赖及契约测试规则。

## 9. 实验与简历

具体评测组合、产品基线、算法消融和实施验收见 [BENCHMARK_PLAN.md](BENCHMARK_PLAN.md)。优先接入 FeatureBench，以 SWE-Milestone 验证连续执行，再用 CooperBench 分析协作机制。

实验同时回答：

1. 同一 Pi 和模型下，任务事实、证据与修复机制是否帮助强单执行？
2. 加入自适应并行后，在哪些任务结构下继续获益？
3. 保持相同预算和独立验收，收益是否跨功能开发、重构、缺陷修复等实例成立？

固定最终验收器，设置普通执行适配/增强执行适配与单执行/自适应执行的组合对照，并加入固定并行基线。无需预先要求每种任务都因多 Agent 获益。

推荐项目标题：

> TripleTeam｜面向长程软件工程任务的自适应执行与可信交付系统

当前可以描述为基于 Pi 的系统原型，说明已实现的状态、候选、验收、恢复及协调启发式。进一步完成后，重点展示：

- 任务级执行适配与工程事实管理；
- 根据依赖、证据和预算调整计算的决策方法；
- 跨任务类型的交付结果、成本、时延及人工操作变化。

使用实际测量数字，分别标明已实现机制、待验证方法和产品目标。具体案例负责把系统讲清楚，不代替系统定位。

## 10. 从用户提供的简历借鉴贡献组织方式

截图中的 SWE-CoA 将表述组织为：协作成本与长程任务问题、交互轨迹管线、SFT/RL 方法、rollout 工程问题及 benchmark 结果。TMA-Agent 同样把长期经验利用问题与记忆机制、学习方法及实验相连。这里参考的是截图所展示的贡献结构，不以截图指标作为本项目的性能依据。

TripleTeam 的对应主线可以是：

> 长程工程任务的协作损耗 → 版本化任务与证据状态 → 计算行动选择及失败修复 → 持续积累可验证进展 → 独立验收下的成本与交付结果。

系统范围保持长程软件工程。内部应选出可以完整实现和比较的主方法，其他机制支撑它。需要把“系统架构”和“算法贡献”分别写清。

| 简历中的贡献层次 | TripleTeam 已有基础 | 需要补齐的实质工作 |
| --- | --- | --- |
| 问题定义 | 协作开销、失败、过期状态与验收模型 | 将目标固定为外部工程目标的交付结果，定义预算和统计口径 |
| 数据与观测 | SQLite 事件、执行、候选、检查与部分 usage | 保留失败成本；记录决策状态、实际动作、新证据及最终结果，获取可比较的对照轨迹 |
| 决策方法 | HIGH/LOW 启发式、四种模式、失败 disposition | 用成本和收益估计选择继续、调查、并行、验证或修复；让不同动作有真实实现 |
| Harness 改进 | 任务输入、协调工具、失败反馈、执行绑定 | 版本化证据投影、可执行承诺、保留有效工作的修复，以及正确恢复 |
| 实验 | 现有 contract tests 与历史小型 E2E | 当前版本跨任务类型的独立验收、强基线、消融、成本与时延曲线 |

### 一个可继续发展的算法方向

记录每个决策点的状态 s（依赖、证据新鲜度、失败类型、剩余预算），可选动作 a，实际费用 c，新产生的有效证据，以及最终验收结果 y。对同类初始任务运行不同策略，估计哪些行动带来有效进展、哪些只增加成本。

先以规则、耗时统计和可解释估计构成基线。样本充分后再训练或校准小型成本/价值预测器，检查是否改善未见任务上的决策。单一确定性策略的日志缺少未选动作结果，不能直接充当无偏反事实训练集。最终奖励来自外部验收，过程进展指标需要防止通过拆碎任务等方式虚增。

这条路径能形成推理时决策与 harness 优化的算法内容。截图里的大模型后训练是另一种实际工作范围；是否加入训练应取决于目标岗位和已观察到的瓶颈，不能仅为简历增加 SFT/GRPO 名词。

### 完成相关改进后的目标简历结构

**TripleTeam｜长程软件工程中的自适应计算与可信交付系统**

- **背景与目标：** 针对跨模块、多阶段工程任务中重复探索、接口耦合及失败返工消耗额外 Agent 计算的问题，构建基于 Pi 的任务级执行系统，以固定预算下的可验证交付为优化目标。
- **决策方法：** 描述实际实现的状态特征、行动选择依据、成本估计和失败策略，并报告相比静态启发式的效果。
- **Harness 机制：** 描述实际实现的版本化证据输入、artifact 兑现、候选级修复与执行恢复，以及它们改变的具体失败行为。
- **实验与结果：** 填写真实任务数量、模型与预算，报告相对强单执行和固定并行的成功率、时延、总费用及消融；保留未获益任务和失败案例。

上述为目标结构。现阶段不能把待实现的预测器、可执行契约或性能提升写成既有成果。
