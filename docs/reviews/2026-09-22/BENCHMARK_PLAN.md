# TripleTeam 评测方案：完成率、费用与长程交付

日期：2026-09-22。本文是实施前冻结的评测设计；下文的待实现项与阶段门禁保留当时语义。后续已完成 FeatureBench / SWE-Milestone 适配、固定策略/消融及独立单题开发检查，操作见 [评测入口](../../BENCHMARK_ADAPTERS.md) 和 [基线配方](../../BASELINE_COMPARISON.md)，实施核对见 [当前状态](../../IMPLEMENTATION_STATUS.md)。正式的产品/模型费用与质量对照仍未运行，没有已证明的性能提升。

项目定位沿用 [PRODUCT_POSITIONING.md](PRODUCT_POSITIONING.md)：面向长程软件工程任务的自适应执行与可信交付系统。评测应覆盖复杂功能、重构、缺陷修复及连续演化中的依赖和返工，不把产品限定为某一类迁移功能。

## 1. 希望证明什么

产品目标：在有明确验收条件的长程软件任务上，比较 TripleTeam、Codex CLI 和 Claude Code 的完成率、总费用、端到端耗时及人工投入。

优先检验两种有实际价值的结果：

1. 相同总预算下，独立验收的完成率提高。
2. 完成率保持在预先约定的接近范围内，总费用降低。

“接近”需要预注册容许差异和统计方法，不能观察结果后临时定义。小规模 pilot 用于估计费用、方差和失败类别，不能据此承诺全面超过成熟产品。

算法目标：解释新增计算何时提升交付、何时用于诊断或验证更合算、何时应该保持单执行。测量自适应策略是否把固定并行的收益保留下来，同时减少依赖等待、重复探索和协作返工。

## 2. 推荐评测组合

| 优先级 | 评测 | 主要回答的问题 | 使用方式 |
| --- | --- | --- | --- |
| 先接入 | FeatureBench v1.1 的 fast 子集 | 复杂功能能否完成，成本与时间如何 | 小规模开发集打通，再在冻结的留出集比较 |
| 核心长程评测 | SWE-Milestone | 连续任务、依赖 DAG、自身历史代码是否导致错误累积 | 保留官方连续模式，逐仓库评估 |
| 机制评测 | CooperBench | 分工实现是否兼容，契约是否减少返工 | 官方合作协议与自定义自适应协议分开 |
| 后续扩展 | SWE-EVO | 较大范围、发布级目标是否能整体完成 | 作为不同任务粒度的外部验证 |

这是按任务结构选择评测的建议；这些评测不预设多 Agent 会获胜。

### 2.1 FeatureBench：最先打通的功能开发评测

官方项目面向复杂功能开发，已有 Codex、Claude Code 等推理适配。fast 包含 100 个实例，评测环境无需 GPU。2026-08-24 发布的数据 v1.1 修订了需求描述；官网当前榜单标注的数据版本仍是 v1.0。[官方仓库](https://github.com/LiberCoders/FeatureBench)

执行决定：选定数据 revision、实例列表和镜像 digest；所有基线重跑相同版本。fast 是子集，结果必须标明范围，不能写成 full 成绩。无需 GPU 指本地任务评测，模型推理由所选服务承担；本机仍需足够的 Docker、CPU、内存和磁盘资源。

主要报告官方任务完成率 `%RESOLVED`，同时保留测试通过指标。部分测试通过不能表述为对应比例的任务已经完整交付。

核对源码发现，辅助汇总脚本默认 `--attempt-mode best`，按评测后的 pass rate 选择尝试；`--merge` 另支持多次尝试中任意成功的统计。[已核对版本的汇总实现](https://github.com/LiberCoders/FeatureBench/blob/8d4e347ec57546685c5a87e8676bf575db022ea6/featurebench/scripts/cal_eval_outputs.py)

本项目主结果采用一次外部试验的最终提交。内部可以规划、重试、探索多个候选，但选择器只能看协议允许的开发证据，并承担全部费用。多次独立重复报告平均结果；不能用隐藏评分替系统选择最佳提交。若另报 pass@k，明确次数、总费用和选择条件。

### 2.2 SWE-Milestone：最贴近长程定位的主评测

论文版本包含 7 个仓库、5 种语言、98 个计分 milestone；任务形成 DAG，连续模式中后续任务基于 Agent 自己此前产生的代码继续进行。其综合 Score 与严格 Resolve Rate 是不同指标。[论文 v4](https://arxiv.org/html/2603.13428v4)

官方仓库已有 Codex、Claude Code 等适配，使用持久容器、Git 提交标签与隔离评测快照。完整镜像集合约 115 个，适合先按仓库验证环境，再决定全量规模。[官方仓库](https://github.com/DeepCommit-ai/SWE-Milestone)

执行决定：使用官方连续模式作为主条件，完整保留可见任务流、依赖解锁、提交和超时规则。不能把每一步重置到标准答案的正确代码后，继续称为连续执行。独立模式可作为诊断，单列其与连续模式的差距。

接入时必须处理本项目的三个边界：

- 提交的是 TripleTeam 权威 integration ref 对应的准确代码树，不能误交用户初始 HEAD 或某个 worker 的工作目录。
- 外部 milestone 需求保持权威；内部 Task 拆分、取消或缩小 scope 不得减少外部计分义务。
- 后续需求按官方规则进入；禁止提前读取尚未公开的规格。持续任务接入和 GoalContract 演进需要明确实现，不能声称当前代码已经支持。

官方当前实现将评测反馈留在评测侧，不提供给被测 Agent；依赖解锁还受 `early_unblock` 等配置影响。adapter 应继承冻结的官方配置，不能额外把隐藏评分接入 Failure Policy。[已核对版本的 orchestrator](https://github.com/DeepCommit-ai/SWE-Milestone/blob/17a8f1593e172e26b36cea15e2b30fb9536c93f5/harness/e2e/orchestrator.py)

此外，该评测提供外部 milestone DAG，因此其成绩可以支持执行和协调能力，不能单独证明 TripleTeam 的 Planner 能从模糊目标中发现正确依赖。后者需要在只给高层目标的任务中另行验证。

### 2.3 CooperBench：定位协作收益来自哪里

该评测让 Agent 处理同一代码库中的不同需求，检验共同结果的正确性和兼容性；初始信息分配属于其合作协议的一部分。[论文及协议](https://arxiv.org/html/2601.13295v2)

用于比较聊天承诺与 artifact 支撑的接口契约、固定并行与受控协作。分别记录文本合并冲突、接口不兼容和最终联合成功，不能把 Git 能合并当作语义兼容。

若中心 Planner 从一开始看到全部需求，允许转为单执行，则标为“基于 CooperBench 任务的自定义自适应执行条件”，与官方轨道分开。它始终是 evaluator adapter，不进入核心运行系统。

### 2.4 SWE-EVO：不同粒度的补充

SWE-EVO 包含 48 个来自 7 个 Python 仓库的任务，使用较高层次的演化需求，涉及跨文件修改和已有行为保持。[论文](https://arxiv.org/abs/2512.18470)

可用于补充发布级目标上的表现。任务规模较大并不自动等于跨任务持续执行；它与 SWE-Milestone 的结果单列。优先完成前两个 adapter，再决定是否增加这一组成本。

### 2.5 对传统榜单的处理

SWE-bench Verified 或 Pro 可以提供熟悉的参照，但不作为本项目唯一主证据。OpenAI 在 2026 年公布的评测审计指出任务描述、测试和验收之间存在问题，并在 7 月的报告中撤回此前采用 SWE-bench Pro 的建议。这是其审计结论，不代表其他评测天然没有问题。[审计报告](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)

对选中的任何评测，都先独立验证环境、空补丁和参考补丁的预期行为。预先定义基础设施故障和失效题目的处理方式，并对所有方法一致应用。若正式运行后发现题目有问题，保留原始成绩，追加有理由和版本记录的修订结果，不能只删除本项目失败的题。

## 3. 比什么：主指标与解释指标

| 指标 | 统计口径 | 对应用户价值 |
| --- | --- | --- |
| 独立验收完成率 | 全部预定实例中，最终提交达到官方完成条件的比例 | 任务到底完成多少 |
| 每个成功交付的总成本 | 所有试验总费用 / 成功交付数，失败费用也计入 | 批量完成工作实际花多少钱 |
| 交付时间 | 请求开始至最终提交的墙钟时间；报告限时完成率 | 用户需要等多久 |
| 回归与进展保持 | 后续有效验收义务上，新通过和新破坏分别统计 | 后续修改是否破坏已有成果 |
| 完成声明可靠性 | 声明完成但外部失败的比例，同时报告声明覆盖率 | 完成报告是否值得信任 |
| 恢复代价 | 固定故障下的完成率变化、额外时间和费用 | 长任务中断后能否继续 |
| 人工投入 | 自主轨道为零；辅助轨道记录次数、主动操作时间和等待 | 用户实际需要照看多久 |

统一记号：`y_i = 1` 表示实例 i 的最终提交通过外部完成判定；`c_i` 表示该试验全部模型费用。

```text
ResolveRate = sum(y_i) / N
CostPerResolved = sum(c_i) / sum(y_i)
FalseAcceptance = count(claimed_complete and not externally_resolved)
                  / count(claimed_complete)
```

零成功时 CostPerResolved 不给有限数值；零完成声明时 FalseAcceptance 未定义，不能写成 0%。BLOCKED、超时、系统崩溃、没有提交的实例仍在任务分母内；单列失败原因。独立 evaluator 自身故障按照事先固定的规则重评相同提交，不给 Agent 偷增一次修复机会。

对 SWE-Milestone 仍使用官方宏平均和计分粒度，额外成本统计注明按 milestone 还是完整仓库试验计。吞吐分母中的目标来自外部固定任务集，不能靠内部多拆 Task 增加“完成数量”。不同 benchmark 不直接平均成一个百分比。

时间至少区分端到端墙钟时间、Agent 活跃时间、验证/集成时间。成功样本 p50/p90 必须同时给成功率，避免大量困难任务失败后“平均更快”。相同 deadline 下的完成率是主要时间比较。

额外的历史成果保持检查只覆盖仍有效的需求。后续规格明确替代的旧行为不能继续作为必须保留的目标。官方评分与新增的最终树保持检查分别报告。

费用包括规划、探索、writer、review、重试、恢复和候选选择；记录缓存和可获得的推理用量，缺失计费项标为未知。模型费用、机器/工具费用分别展示，再给有明确口径的总成本。不同 tokenizer 的 token 数不能直接当作相同计算量；订阅价格也不能折算成每题零费用。

机制解释指标只用于诊断：重复探索成本、接口不兼容次数、返工费用、废弃候选、验证耗时、关键路径等待。低消息数、少 token 或更多 Agent 本身都不能证明更好的交付。

## 4. 两类对照，分别回答产品与算法问题

### 4.1 产品对照

- TripleTeam + 固定模型配置。
- Codex CLI + 固定 CLI 与模型配置。
- Claude Code + 固定 CLI 与模型配置。

使用同一实例、起始代码、可见信息、网络条件、机器资源和总预算。允许各产品使用预先声明的正常能力；若有原生团队/子 Agent 配置，须明确启用情况，所有子执行计入同一预算。基线调参限于开发集，不能只认真优化 TripleTeam。

这一组说明用户采用产品的端到端效果。模型不同时，明确是“系统 + 模型”的组合比较，不能单独归因给协调算法。同模型可以对齐时，补充相同模型实验，并记录 reasoning 等配置差异。

### 4.2 算法对照

固定 Pi、模型、工具、可见检查和总预算，比较：

1. 强单执行：允许充分 debug、测试和失败修复，使用同一交付基础。
2. 固定并行：选择预声明的并行数，例如 2 或 4。
3. 当前启发式协调策略。
4. 增强自适应策略。
5. 关键消融：去除可执行契约、替换为普通重试、去除接口先行等。

无需一开始跑满全部组合。先用强单执行和完整方法确认是否有收益，再在冻结协议下定位贡献。当前启发式必须保存为可复现基线，不能只拿弱化后的单执行比较。

分别画总预算—完成率、deadline—完成率曲线；预算上限用 pilot 估计后预先冻结。每条曲线注明另一种资源约束，所有方法保留失败实例。并行增加总计算还是只减少墙钟时间，应从两条曲线中说明。

## 5. 冻结协议

以下是拟新增的评测清单字段，不是当前已支持的 CLI 参数：

```text
benchmark name / data revision / evaluator commit / instance IDs
image digests / source base commit / visible task payload hashes
system commit / Pi snapshot / CLI version / model / provider / reasoning settings
policy version / tool configuration / network policy / CPU / RAM / concurrency limits
decision mode / cost budget / deadline / retry policy / run replicate ID
price snapshot / usage accounting method / missing-data policy
submission selection rule / hidden evaluator feedback policy
```

自主轨道固定 `noninteractive`：禁止人工答复、steer、改代码和临时修改验收。允许记录 DecisionRequest；无法授权时返回 BLOCKED。普通技术困难仍由系统搜索、调试、测试、重规划。具有完整任务规格的主评测中，BLOCKED 计未完成。

产品中的必要人工决策另设辅助轨道；必须询问产品语义或权限的样本单独评估是否正确请求决策，不能通过擅自猜测获得“自主成功”。不能把辅助轨道混入自主成绩。

隐藏验收和参考解只在 evaluator 侧。系统的 Acceptance 依据协议允许的可见证据，官方 hidden verdict 只用于独立评价二者是否一致。额外提供隐藏测试失败信息，会改变任务条件。

有限预算内允许系统自行重试；最终提交选择不能读取隐藏评分。重复运行用于统计不确定性，不能在看过测试成绩后只展示最好的 seed。模型 API 未提供 seed 时记录重复编号和随机配置，不虚构可复现的模型随机种子。

先划分开发集和留出集，尽量按仓库避免泄漏。SWE-Milestone 只有 7 个仓库，其连续 milestone 相互依赖；不能把 98 个节点当作 98 个独立样本计算置信区间。报告逐仓库结果、配对差异和聚类不确定性；仓库数量少时限制结论范围。用过的 pilot 不再标为未见测试集。

## 6. 交给用户跑正式 benchmark 前的实施验收

| 阶段 | 必须交付的内容 | 验收条件 |
| --- | --- | --- |
| G0：结果与费用可信 | 修复审查 R1/R2；失败/中断计费；无人工模式；总预算控制 | 可控假运行不会错误宣布验收，不漏记已知费用；达到限制能停止并落盘 |
| G1：评测接入 | FeatureBench 导出适配、固定运行清单、独立 evaluator、汇总 | 空补丁/参考补丁可验证环境；结果绑定实际集成树；所有预定实例均有记录 |
| G2：策略开发 | 真实失败指纹与差异化修复、契约证据、成本反馈、强基线 | 开发集轨迹能解释每次加算力和改策略；同预算比较能成立 |
| G3：连续执行 | SWE-Milestone adapter、持久代码状态、官方任务流和提交映射 | 小型受控 DAG 不偷看未来规格、不重置标准答案、不把提交当验收 |
| G4：正式交付 | 冻结版本、配置、运行说明、结果格式和绘图脚本 | 用户可重复启动三套系统，获得完整失败记录、费用和独立验收结果 |

G0/G1 应尽早进行，pilot 的真实失败用于指导 G2，避免先堆完整套算法再发现瓶颈不在协调。无需等所有产品功能完成才建立评测回路。

计费应通过 Pi 公共事件/API 与可用的服务端用量核对，不能只在成功返回时累计。并发执行需要统一预算账本和在途请求额度管理；无法精确中止的请求须记录超额及界限，不能声称绝对不会超支。

恢复专项另设可重复的故障条件，对各系统提供一致的外部恢复机会，测量最终完成率与额外成本。epoch 等内部保证通过 TripleTeam 的确定性测试证明；不能因为看不到竞争产品内部状态，就判定其没有恢复能力。专项成绩不混入公开 benchmark 官方成绩。

目前 G0–G4 尚未完成；审查文档和缺陷复现不能替代这些实施验收。[代码审查与复现说明](REVIEW.md)

## 7. 建议实际运行顺序

1. 无模型环境验证：核对 Docker、数据、镜像、补丁输入输出和评分口径。
2. 开发 pilot：从 FeatureBench fast 冻结 20–30 题，比较强单执行与 TripleTeam，另取相同条件的 Codex/Claude Code 产品基线。用于发现故障和估算预算。
3. 长程接入 pilot：选预声明的开发仓库运行完整连续任务流，检查状态延续与提交协议。不要只截取获胜节点。
4. 正式评测：冻结方法，在未用于开发的任务/仓库上跑多个预算档；资源允许时重复。完整公开集成绩包含开发部分时，分别标记开发和留出结果。
5. 有端到端收益后运行关键消融和 CooperBench；用轨迹解释减少的是哪类无效计算，以及哪些任务仍适合单执行。

预算由 pilot 的实际单题/单仓库成本乘以实例数、方法数、预算档和重复数估计，另计环境及失败开销。本文不承诺固定美元价格或性能目标已经达成。

最终材料至少包含：配置清单、逐实例输出与树标识、官方验收报告、全量用量账、预算/时间曲线、消融、失败案例和一份可复现说明。简历数字仅从冻结的结果表生成。
